An AI Agent Pipeline That Runs My Job Search

I turned a manual, repetitive workflow into a scheduled AI agent pipeline. Every morning it searches two job boards, screens postings against rules I set, evaluates fit against my resume, and hands me a ranked shortlist. I make every decision that matters. It does the legwork that used to take hours.

The problem

A thorough job search is program work. Every posting needs the same steps: find it, read it, check pay, location and seniority, compare it to my experience, estimate how well a resume would score in applicant tracking systems, and decide whether it's worth a tailored application. I was doing all of that by hand, one posting at a time, using generic searches that returned far more noise than signal.

I already had a well-tuned evaluation process: a reusable Claude skill that scores fit and builds tailored resumes from my master resume. What I didn't have was the operating layer around it, the part that finds the work, filters it, runs the process consistently, and reports back.

How it works

Design decisions

1. One source of truth for the decision logic.My first plan was a Python and LangGraph pipeline with its own scoring prompt. Partway through, I realized that would create a second copy of logic I already trusted in my resume skill, and the two would drift apart. I scrapped that approach. The pipeline now calls the same skill I use by hand, so a fix in one place improves both. Governance applies to prompts the same way it applies to policies.
2. Rules live in a plain file, not in the code.Target titles, location rules, exclusions and limits sit in an editable config file the pipeline reads fresh every morning. When I decided to exclude engineer and architect titles, or to keep Associate Director roles, I changed a line of text. I didn't have to touch the automation.
3. Hard rules only on hard facts.A posting is skipped for pay only when it states pay below my floor. If pay isn't posted, the pipeline estimates a range, labels it as an estimate, and leaves the decision to me. An automated filter shouldn't throw out opportunities on a guess.
4. Cheap filters before expensive evaluation.Each full fit evaluation reads my entire master resume and runs a keyword analysis, so the pipeline screens by title, location, pay and history first and caps full evaluations at 10 per run, Tier 1 AI roles first.
5. A memory so work never repeats.Every posting the pipeline looks at is logged with the outcome. Nothing is evaluated twice, and the log doubles as an audit trail of what was considered and why it was dropped.
6. Tiered targeting, including a conditional tier.AI program and governance roles rank first, then program and portfolio leadership, then local project management roles. Business analyst roles are searched too, but they're kept only when the work centers on AI or emerging technology and the pay is right, and they're labeled "step back in scope."

Guardrails

GuardrailHow it works
Recommend onlyThe pipeline never applies for a job and never builds a resume on its own. It produces a shortlist.
Human gateI review every shortlist and decide what moves forward. Tailored resumes are built with me present, because that step asks me questions before writing.
Truth sourceFit is judged only against my master resume. The pipeline can't claim experience the master doesn't document.
Labeled uncertaintyEstimated pay and ATS scores are labeled as estimates, and the ATS estimate is calibrated against real Jobscan results.
Data stays localMy resume, config and logs stay in a folder on my own computer. The pipeline reads them there and writes the shortlist back.
DisclosureEvery shortlist states that listings were found with AI-assisted search and should be verified with the employer.

What broke, and what I changed

The first scheduled run reported "succeeded" and produced nothing. It had stopped about a minute in. I ran the workflow end to end by hand to find out why, and that surfaced three more problems:

  • Sorting by newest was mostly noise. On one job board, date-sorted results were dominated by unrelated contract engineering roles. Sorting by relevance and widening the window to three days, with the history log preventing repeats, produced far better matches.
  • Some job IDs were temporary. One connector's IDs expired between sessions, so the log now records each posting's permanent link instead.
  • A 24-hour window was too narrow for a first run and too fragile day to day. The log makes a wider window safe.

I rewrote the task's instructions to address each one, including an explicit requirement to finish every step and report any failure plainly.

Lessons learned

A "succeeded" status is not evidence. The run that produced nothing reported success. Automated work should be judged by its outputs, so I check that the shortlist and log actually changed, not that the job ran.

Decision logic should exist once.Duplicating prompts across tools is the AI version of maintaining two copies of a policy. Pointing automation at the same governed logic people use keeps them consistent.
Put the knobs where people can reach them.Most of the tuning after day one was configuration, not code. Keeping rules in a readable file let me adjust the system in minutes.
Calibrate before you trust.The first run's output shaped five rule changes. A pipeline is a program: it needs a feedback loop, and the first few cycles are where most of the value gets found.

Tools

Built with Claude as my build partner: Claude scheduled tasks for the daily run, Indeed and Dice connectors for search, my resume-tailor skill for evaluation, and Python for document generation and logging. The design, rules and governance decisions are mine; Claude did much of the building, which is exactly how I'd expect an AI-enabled program manager to work.
