Case study

Sev1 Incident Response Agent

I designed and deployed a Copilot Studio agent that helped incident commanders triage Severity 1 outages faster, and challenged them when they locked onto the wrong cause. Over three months, Sev1 time to resolve fell 15%, alongside improved monitoring and Datadog's Bits AI.

SettingNational healthcare SaaS platform, HIPAA-regulated
My roleIncident commander; designed, built and governed the agent
UsersTeam of 2 incident managers, 1 IT director and 1 change manager
PlatformMicrosoft Copilot Studio, Microsoft Teams, Microsoft 365
Outcome15% faster Sev1 resolution over 3 months (shared result, see Outcome)

The problem: starting every Sev1 from zero

Incident commanders joined each Severity 1 call with almost nothing to start from. The platform saw both recurring incidents and a steady stream of new ones, but dependencies, application behavior and past Sev1s were poorly documented.

The first minutes of every incident were the hardest. Commanders had to form and test hypotheses from memory while the outage was live, and the same issues kept coming back because follow-up actions weren't captured well enough to prevent them.

The business need was clear: shorten time to resolve, reduce the load on commanders at the start of an incident, and build a better record so repeat incidents became easier to solve.

How it worked

Design decisions

1. Built to challenge the team, not just speed it up.The agent had four jobs: find similar past incidents, propose alternative hypotheses ranked by likelihood, recommend tests and corrective actions, and suggest causes the team hadn't considered. That last job was deliberate. Under pressure, incident teams lock onto the first plausible cause, and the agent's role was to keep other options on the table.
2. Grounded in what the team was already producing.Security controls blocked the agent from connecting to Datadog, our system of record for Sev1s. Rather than wait for an integration, I designed around it. My hourly status emails, which I also logged in Datadog, became the agent's running incident record. The live Teams chat gave it current actions and discussion. Incident commanders pasted in Datadog and Bits AI monitoring data by hand to ground its analysis.
3. Available where the work happened.Commanders reached the agent from inside Teams, so they didn't have to switch between the incident chat and the Datadog or Azure monitoring screens during the most demanding minutes.
4. Separate tools for separate jobs.The agent handled reasoning. Teams Copilot handled documentation, generating periodic incident summaries from the call transcript with standard prompts. Keeping the two apart kept each tool focused and its output easier to judge.
5. A shared prompt library.Our IT director had set out the questions he wanted asked on every Sev1. I used his list as the base for a set of detailed, reusable prompts, so every incident started from the same leadership-defined questions and everyone used the agent the same way.

Guardrails

The agent could advise but never act, and it had no path to patient data.

Recommend onlyThe agent could not page people, run commands, change systems or update records. Its output was text for an incident commander to read.
Two human gatesAn incident commander judged each recommendation before passing it to the team, and the team decided whether to run a test or corrective action.
Corroboration before actionCommanders weighed a recommendation by checking it against Bits AI findings, live monitoring, past incidents and team feedback, not by the agent's confidence.
Data boundary by designPatient health information lived only in an isolated Azure production environment, reachable solely through jump boxes and VDI. The agent ran on the separate corporate network, using email, Teams and manually supplied metrics, so it had no path to PHI.
Approved platformThe agent ran in Copilot Studio inside the company's Microsoft 365 environment, under its existing security and access controls.

Outcome

Sev1 time to resolve fell 15% over three months. The incident team adopted the agent quickly, because it addressed a problem they all faced, and the shared prompts gave them a consistent way to start every investigation.

That 15% came from three changes that reinforced each other:

  • Better monitoring. The monitoring team kept building new dashboards from our lessons learned and improved documentation.
  • Datadog's Bits AI, used to investigate monitoring data.
  • This agent, used to generate and challenge hypotheses.

Because all three improved together during live incidents, the agent's individual share can't be isolated, and I don't claim it. The honest result is a combined one, and the lesson is that attribution has to be designed in before launch, not reconstructed afterward.

Lessons learned

Confident and wrong is the default without grounding.Early on, the agent was often confidently wrong. Feeding it real monitoring data from Bits AI cut that sharply. The rule I took away: an AI system's confidence is not evidence, and its value depends on what it's grounded in.
The best grounding came from a habit, not an integration.The monitoring team began posting Bits AI findings and monitoring data directly in the incident Teams chat. Because the agent read that chat, it picked up the data automatically and focused its answers, which cut down the manual pasting we had been doing. Sometimes the fastest fix to a data gap is a change in team habits.
Security constraints shape the design, so plan for them.Without Datadog access, commanders copied data between tools by hand. A direct, security-approved integration would have made the agent faster and better grounded. Next time I'd start that approval in parallel with the build, rather than treating the constraint as fixed.
Feedback has to be built in, not requested.Nearly all testing and feedback happened during live incidents, and the pace of daily work made structured feedback hard to collect. That improved the agent quickly but left no baseline and no repeatable test.

What I'd do differently

  1. Build a small evaluation set from past Sev1s before launch, so improvements can be measured against a baseline.
  2. Add one-click feedback on each recommendation (useful or not useful) to capture signal without slowing anyone down.
  3. Stagger changes, or track which tools were used on each incident, so the agent's contribution can be measured on its own.
  4. Begin the security review for a direct monitoring integration on day one.
