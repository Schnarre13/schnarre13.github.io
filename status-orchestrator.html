AI Status Orchestrator

A multi-agent workflow that turns a week of raw program inputs into a decision-ready status report, an updated RAID log and a budget variance analysis. Agents do the assembly. Code checks the numbers. A person approves before anything reaches leadership.

Why I built it

In a transformation office, most of the weekly effort goes into assembly: chasing workstream updates, pulling risks out of meeting notes, reconciling budget actuals to plan, and turning all of it into something an executive can act on. That used to take a PMO team. My operating rhythm toolkit describes which parts AI can take over. This build puts that into practice as a working pipeline, so I can show how the orchestration, guardrails and handoffs work, not just describe them.

How it works

Each week the program manager drops in four inputs: workstream updates, a meeting transcript, budget actuals and the current RAID log. The orchestrator runs this graph:

  1. Collect loads the week's inputs.
  2. Two branches run in parallel: the RAID agent proposes new risks, issues, assumptions, dependencies and Value Risks, and the earned value step calculates CPI, SPI, variances and forecast at completion for each workstream.
  3. The status agent waits for both, then drafts an executive report that leads with decisions needed.
  4. The validator checks the draft. If anything fails, the draft goes back with the specific findings, up to three times.
  5. The run pauses for a person. Approve, edit or reject.
  6. On approval it publishes the report, the updated RAID log, the budget metrics and an audit log of every step.

Controls built into the design

Arithmetic in code, not in the modelEarned value is calculated deterministically. The status agent is told to use the figures as given, and the validator checks that it did.
Every RAID item must quote its sourceEach proposed item carries an exact quote from the meeting transcript or a workstream update. If the quote isn't in the sources, the item is dropped automatically, so the agent can't invent a risk.
A validator between the model and peopleEvery number in the draft must appear in a source. Required sections must be present. Every workstream must be covered. A draft that fails is rewritten before anyone sees it.
A real approval gateThe graph stops and waits. Rejected drafts publish nothing. New RAID items are logged as "Open (pending owner confirmation)" until a person assigns them.
A full audit trailEach run records what every step did: how many drafts it took, what the validator caught, and who decided what.
Value Risk as a RAID typeThe RAID agent flags anything that questions whether a deliverable will move the metric it was approved for, such as a use case launching without a baseline.

Three orchestration approaches I've used

  • Microsoft Copilot Studio: an agent that joined Sev1 incidents in production. Case study
  • Claude scheduled tasks with connectors and a reusable skill: a daily pipeline that searches job boards, screens against rules and evaluates fit, unattended, with me reviewing the output. Case study
  • LangGraph with the Claude API: this build, a code-level graph with parallel agents, a validation loop and a human approval gate.

The low-code tools get a team running fastest. Code-level orchestration gives the most control over guardrails and auditability. The design principles are the same in all three: deterministic work in code, the model only where language is needed, and a person approving anything that leaves the program.

Limits and next steps

  • The validator checks numbers, sections and coverage. It can't judge whether the tone is fair or the overall status is right; that's the reviewer's job, which is why the gate exists.
  • The sample inputs are files. In a real program the collector would read from the actual systems (project tracker, meeting platform, finance system) through connectors, and the run would be scheduled ahead of the weekly status call.
